# 總務服務中心規格書草稿

最後更新：2026-08-24

## 1. 文件目的

本文件用來重新整理總務服務中心在測試區要補強的產品規格。內容先以實務需求為準，分別確認門市視角與總務視角，再轉換成測試區開發任務。

本文件不是既有程式碼盤點，也不是 migration 執行清單。任何資料庫、API、UI 開發都必須等規格內容討論確認後，再拆成具體任務。

## 2. 總務服務中心定位

總務服務中心不是單純的報修系統，而是公司總務工作的紀錄與協作中心。

目前總務負責的工作方向包含：

1. 庶務類採買。
2. 庶務類庫存與流向管理。
3. 設施、設備管理與維修派工。
4. 設施、設備、料件廠商建立，以及詢價、比價、議價與廠商品質紀錄。
5. 各門市水費、電費、電話費等帳單金額與繳費狀態紀錄。
6. 各設施、設備、料件相關請款紀錄。

因此系統需要同時支援兩種使用脈絡：

1. 門市端：提出需求、補充資料、配合執行、追蹤進度。
2. 總務端：受理、評估、採買、派工、調撥、記錄費用、管理廠商與請款。

## 3. 門市端需求

### 3.1 門市端角色定位

門市不是總務管理者，也不需要看到總務內部完整後台流程。門市端主要扮演以下角色：

1. 提出需求。
2. 補充資料。
3. 配合總務指示執行。
4. 追蹤自己提出或自己門市相關需求的處理進度。
5. 對完成結果進行確認。

門市端的核心原則是：

> 門市不需要知道總務內部做了幾個管理流程；門市只需要知道自己提出的事情目前處理到哪裡，以及是否需要自己配合。

門市端建立需求單時，預設只能替自己被指派管理的門市建立需求。若店長只管理一間門市，系統應自動帶入該門市並鎖定；若店長被指派管理兩間以上門市，才需要讓店長在自己的門市清單中選擇。

系統管理員或具備全域代建權限的使用者例外。當系統允許使用者在新增需求畫面選擇某間門市，就代表該使用者可以代替該門市送出需求單，前端選項與後端建立權限必須一致。

### 3.2 門市可提出的需求類型

門市端主要需要以下需求入口。

#### 3.2.1 設備 / 設施維修需求回報

門市可回報設備或設施異常，例如冷氣、冰箱、招牌、門鎖、水電、燈具、網路設備、監視器等。

門市回報時至少需要提供：

1. 所屬門市。
2. 問題類型：設備故障、店內設施 / 環境問題，或不確定請總務判斷。
3. 若為店內設施 / 環境問題，再選擇現場狀況類型，例如漏水、電力異常、門鎖異常、地板牆面損壞、病媒或環境消毒等。
4. 發生位置，例如樓層、櫃台內 / 外、倉庫、後門、廁所等。
5. 問題描述。
6. 聯絡人與聯絡方式。
7. 照片或附件。

門市端不需要先判斷標的是設備或設施，也不應因為找不到標的而無法回報。系統應先讓門市用新手可理解的方式判斷「是不是某台設備壞了」。若選擇設備故障，表單才提供設備編號、設備名稱或位置搜尋；若選擇店內設施 / 環境問題，則不顯示設備選擇器，只顯示漏水、病媒、門鎖、牆面地板等現場狀況按鈕與樓層 / 區域 / 補充位置；若選擇不確定，則直接描述問題並交由總務受理後判斷。

若門市選擇設備故障且知道設備編號、條碼、名稱、品牌型號、位置或區域，才可在選填搜尋入口中協助帶入既有設備。門市選取後，系統自動帶入設備主檔 ID；未選取時，總務受理後再判斷是否補建主檔、綁定既有設備或直接派工處理。

總務受理後，門市可看到公開進度與目前狀態。

#### 3.2.2 添購申請

門市需要添購庶務用品、設備、耗材或料件時，統一使用「添購申請」入口。

添購申請不拆成多個入口。表單中再選擇添購類型，例如：

1. 庶務用品。
2. 設備。
3. 設施相關物品。
4. 料件 / 耗材。
5. 其他。

門市提出添購申請後，不代表一定採購成功。總務需要判斷是否採買、改由庫存出庫、改由其他門市調撥，或駁回。

#### 3.2.3 料件需求

門市只需要提出「我需要這個料件」與用途，不需要指定來源門市或庫存位置。

料件來源由總務判斷，可能是：

1. 從總部庫存出庫。
2. 從其他門市調撥。
3. 重新採購。
4. 不核准或改用替代方案。

#### 3.2.4 資產異動配合

資產異動不是門市自由發起的主要流程。設備移入、移出、報廢、安裝、盤點異常處理等，原則上由總務規劃並指示門市配合。

門市端需要能看到自己要配合的事項，並回報執行結果，例如：

1. 已收到設備。
2. 已完成移出。
3. 已完成安裝確認。
4. 已依指示拍照回傳。
5. 異動結果有問題，需要總務再確認。

### 3.3 門市進度追蹤

不管是維修、添購、料件需求或資產異動配合，門市都需要追蹤總務目前處理到哪。

門市端應有一個統一的「我的總務需求」或「我的需求進度」列表，而不是讓門市分散到很多模組查詢。

第一版門市端統一使用「我的追蹤」追蹤所有已送出的總務需求單，以及總務指派給門市配合處理的待辦事項。維修、添購 / 補充、料件需求都不再拆成不同的門市追蹤入口。

列表應至少顯示：

1. 需求編號。
2. 需求類型。
3. 門市。
4. 主旨 / 項目。
5. 目前狀態。
6. 最近公開進度。
7. 建立時間。
8. 是否需要門市回覆或確認。

門市端「我的追蹤」應以進度條呈現需求目前走到哪個節點，讓店長不需要閱讀總務內部流程也能快速理解。進度條由系統依主狀態自動判斷，不由門市或總務手動輸入百分比。

第一版門市進度條節點為：

1. 送出。
2. 總務接手。
3. 安排處理。
4. 你確認。
5. 完成。

門市端顯示狀態需使用店長看得懂的語言，避免直接呈現太多內部流程字眼。例如系統主狀態為已受理時，門市端應顯示「總務已接手」；系統主狀態為處理中時，門市端應顯示「安排處理中」。詳情頁最上方需優先回答「現在狀態」、「門市目前需不需要操作」、「處理方向」與「負責單位」，讓新手店長不必閱讀完整紀錄也能判斷下一步。

門市端的狀態卡與最新進度不可直接重複顯示後端內部流程文字。若公開進度包含「承辦角色」、「後續處理方式」、「維修工單」或「工單中心」等內部流程資訊，門市端需轉譯成摘要，例如「總務已接手，正在安排後續處理」或「總務正在安排處理，有新進度會更新在這裡」。系統仍可在資料庫保留完整流程文字供總務端追蹤，但店長端第一眼不需要知道工單中心或分流細節。

若需求狀態為待補資料或待總務複核，應在進度條附近顯示提醒文字。若需求已駁回或取消，則以終止狀態呈現，並顯示駁回或取消原因。

門市端「我的追蹤」需顯示處理紀錄區，整合系統公開事件與門市可見留言。門市不需要看到總務內部備註或內部事件，只需看到與自己判斷進度、補資料、確認完成有關的公開紀錄。

處理紀錄在門市端應以「最新回覆」優先顯示，預設只呈現最近幾筆公開進度與留言；完整處理紀錄可由門市自行展開。這樣已受理或處理中的需求不會因歷程過長，讓店長找不到目前總務說了什麼。

門市端可在「我的追蹤」新增公開留言，用於補充現場狀況、詢問進度或回覆總務。門市不需要選擇留言公開性，門市留言一律視為公開協作紀錄。留言輸入區在介面上應命名為「補充現場狀況給總務」，避免新手店長誤以為只是一般留言，而不知道可以用來回報現場變化或補充照片。

### 3.4 門市可見狀態

門市端採用較完整的狀態流程：

1. 待受理。
2. 待補資料。
3. 待總務複核。
4. 已受理。
5. 處理中。
6. 待門市確認。
7. 已完成。
8. 已駁回。
9. 已取消。

不同需求類型可使用同一套主狀態，但在處理中階段顯示不同的公開進度文字。例如維修顯示派工中，添購顯示採買中，料件需求顯示調撥中或採買中。

### 3.5 完成確認

門市需要按「確認完成」才算正式完成，尤其是維修類需求。

原因：

1. 總務可能接到廠商通知已完成。
2. 但實際完成結果可能不符合門市預期。
3. 門市若沒有確認機制，雙方容易對「完成」定義不一致。

因此流程上應區分：

1. 總務標記處理完成：狀態變成待門市確認。
2. 門市確認完成：狀態變成已完成。
3. 門市不同意完成：需求回到處理中或重新評估，並留下原因。

### 3.6 門市待辦動作

門市端「我的追蹤」除了顯示進度，也需要在特定狀態提供可執行的待辦動作。

當需求狀態為待補資料時，門市端需提供補充資料回覆區。門市必須填寫補充說明，並可依總務要求上傳照片或附件。送出後，需求狀態改為待總務複核。

當需求狀態為待門市確認時，門市端需提供兩個動作：

1. 確認完成：狀態改為已完成。
2. 回報有問題：必須填寫問題原因，可上傳照片或附件，狀態退回處理中，讓總務重新處理。

門市端待確認畫面需以「確認現場結果」為第一優先，而不是先呈現完整明細。我的追蹤列表應以「請你確認」標籤提醒店長此案需要自己處理；右側詳情最上方需顯示「請確認現場是否已完成」行動卡，直接提供確認完成與回報有問題兩個主動作，並在回報有問題未填原因時以小警示提醒、聚焦到原因欄位。原始回報內容、營運影響、附件照片與處理紀錄保留在下方作為輔助確認資料。

若該需求已分流並連結維修工單，門市在「我的追蹤」執行確認完成或回報有問題時，系統也需同步更新對應維修工單狀態，避免工單中心與門市端進度不同步。

## 4. 總務端需求

### 4.1 總務端角色定位

總務端不是單純被動接收門市需求，而是需求受理、判斷、分流、執行與紀錄的主要角色。

門市提出需求後，是否受理由總務判斷。總務需要能在系統中留下判斷結果、處理方式、處理進度與必要原因。

總務端的核心工作包含：

1. 判斷需求是否受理。
2. 將需求分流為維修派工、庫存出庫、門市調撥、採購或駁回。
3. 管理設備、設施、料件、供應商與廠商資料。
4. 紀錄詢價、比價、議價、派工與請款過程。
5. 將可公開給門市看的進度同步回門市端。
6. 對內保留總務處理備註與判斷依據。

### 4.2 總務工作台

總務端需要依工作狀態分成不同工作台，方便總務承辦處理。

建議至少包含：

1. 待受理。
2. 已受理 / 評估中。
3. 維修派工。
4. 添購採買。
5. 庫存出庫 / 調撥。
6. 駁回。
7. 待門市確認。
8. 已完成。

「駁回」需要作為明確狀態與工作台篩選條件。總務駁回時必須填寫駁回原因，門市端也要能看到駁回原因。

駁回原因至少需要支援：

1. 不屬於總務處理範圍。
2. 資料不足，需重新提出。
3. 已有替代處理方式。
4. 不符合採購或維修條件。
5. 重複申請。
6. 其他，需填寫原因。

駁回採用「固定原因 + 補充說明」。

固定原因包含：

1. 不屬於總務 / 工務處理範圍。
2. 資料不足，請重新提出。
3. 重複申請。
4. 不符合採購 / 維修條件。
5. 已有替代處理方式。
6. 其他。

補充說明必填，且門市端看得到。

第一版不做跨門市需求合併。若總務判斷為重複申請，先以駁回原因與補充說明處理。

### 4.2.0 新需求單、總務需求工作台與工單中心界線

門市端送出的新需求單以 `ga_service_requests` 作為第一版統一資料來源。

總務需求工作台是新需求單的總務端主工作台，同一張列表需涵蓋待受理、待補資料、待總務複核、已受理、處理中、待門市確認、已完成、已駁回與已取消。總務不應為了看待受理與處理中案件而在不同功能頁反覆跳轉。

總務需求工作台也需承接設備建檔 / 貼標流程中「待總務複核」的設備照片任務。門市上傳貼標位置照片後，該設備應出現在同一頁的「待總務複核」篩選視角，讓總務可直接查看設備照片與貼標位置照片，並執行「照片正確，完成建檔」或「退回重拍」。

總務需求工作台的各狀態篩選卡需顯示該狀態件數，且件數需包含同一狀態視角下的需求單與設備建檔 / 貼標複核任務，避免總務不知道某個狀態底下仍有待辦。

待受理只是總務需求工作台中的一個狀態視角。當需求剛由門市送出時，總務在同一工作台判斷是否受理、駁回、要求補資料，以及決定後續分流方向。

工單中心與既有 `maintenance_requests` 流程屬於後續執行或舊維修資料管理視角，不應再作為門市端提出需求的主要入口。未來若新需求被總務受理並分流為維修派工，才可由系統建立或連結到維修工單；但門市第一入口仍是新增需求。

工單中心第一版應以「維修派工收件匣」設計，而不是單純維修資料表。預設需顯示近期或未完成的派工工單，不應因維修回報日期篩選而讓已受理轉出的工單消失。左側列表需讓總務 / 工務快速看到門市、問題、來源與下一步；右側詳情最上方需顯示「目前要做什麼」，依已受理、處理中、等待門市補資料、等待廠商、等待料件、待門市確認與已完成等狀態自動提示下一步。工單中心不得顯示或受理未受理需求；受理、駁回、補資料與分流必須回到總務需求工作台執行。工單中心的主要任務是追蹤維修執行、廠商 / 保固 / 料件狀態、施工處理與門市確認，不再承擔門市提出需求或總務初步受理的入口角色。

工單中心的狀態篩選應使用可點擊狀態卡片，而不是下拉選單。卡片需顯示「全部工單、已受理、處理中、已完成」等可在工單中心處理的狀態件數，且件數需依目前門市與關鍵字條件同步變動；未受理需求不應出現在工單中心的狀態卡或列表中，避免總務 / 工務誤以為可在工單中心受理。

工單中心的右側詳情需先幫新手總務看懂門市現場，而不是先要求他填處理紀錄。詳情順序應為「現場狀況總覽、附件照片、設備 / 項目線索、目前處理狀態、下一步處理、處理紀錄」。現場狀況總覽需優先顯示門市、發生位置、問題類型、聯絡窗口與門市描述，讓總務第一眼能判斷是否要找廠商、查保固、等料件或請門市補資料。

若工單是由總務需求單分流建立，工單中心需同步顯示原始總務需求單的門市附件照片與公開留言附件照片，不可只顯示舊維修工單附件。這些照片是總務判斷現場狀況的主要依據，需在詳情前段露出並標示來源。門市端「我的追蹤」與總務端「總務需求工作台」也都需在留言卡片中直接顯示圖片縮圖，避免使用者以為留言附件沒有上傳成功。

工單中心的更新介面需提供新手總務可理解的快捷下一步，例如「總務自行處理」、「聯絡廠商」、「等待報價」、「已安排到場」、「缺料件」、「送門市確認」。點選快捷動作後，系統需自動帶入處理階段、處理方式、公開 / 內部可見性與預設紀錄文字，總務再依現場狀況微調。處理方式應以選項為主，例如內部自行處理、廠商處理、原廠 / 保固、等待料件、暫停等待確認或其他，避免新手從空白欄位猜要填什麼。

工單中心的下一步處理區預設不可攤開所有技術欄位。新手總務應先看到「已選下一步」摘要、門市是否看得到、處理方式與可微調的進度文字；處理動作、處理階段、承辦人、處理方式、可見性與日期等欄位應收在「進階設定」中，需要時才展開。這樣工單中心的操作焦點會落在判斷下一步，而不是讓使用者像在維護資料表欄位。

因此第一版資訊架構應收斂為：

1. 門市端新增：新增需求。
2. 門市端追蹤：我的追蹤。
3. 總務端總控：總務需求工作台。
4. 總務端維修執行細節：工單中心。
5. 總務端其他後續執行：依受理分流進入採購、庫存出庫、調撥或資產異動。

原本門市端的「新增料件申請」與「我的料件申請」不再作為獨立入口。料件、耗材與庶務需求統一由「新增需求」中的添購 / 補充類型承接，並在「我的追蹤」追蹤。

第一版先落地維修派工分流：當總務在總務需求工作台按受理，且後續處理方式選擇「維修派工」時，系統需自動建立或連結一張維修工單，並在需求單上保留工單連結。工單中心後續更新公開進度時，需同步回門市端「我的追蹤」的公開進度與進度條狀態。

工單中心按「處理完成，請門市確認」時，系統需將維修工單進度設為等待門市確認，並強制以公開進度同步回門市端需求單。此時工單中心不可再呈現一般處理表單作為主要下一步，而應顯示「已送門市確認，等待門市回覆」的唯讀提示；門市確認完成後工單與需求單完成，門市回報有問題時則退回處理中並重新出現在工單中心待處理。

總務需求工作台需支援尚未轉入專責模組案件的節點推進與內部處理紀錄，也需支援總務標記「送門市確認」。但若需求已分流為維修派工並連結維修工單，後續廠商、施工、料件、處理進度與送門市確認必須回工單中心更新；總務需求工作台僅保留原始需求、照片、留言、處理紀錄檢視與「前往工單中心」導向，避免同一件維修在兩個地方都能編輯。門市端看到的公開進度原則上由系統依流程節點與分流方式自動產生，不要求總務每次手動填寫公開文字。

已連結維修工單的需求，其「前往工單中心」導向必須帶入對應工單識別，工單中心開啟後需自動選取該工單，讓總務 / 工務不需要再回到列表搜尋同一案件。

總務需求工作台的需求詳情需顯示處理紀錄區，整合系統事件、門市留言、總務公開紀錄與總務內部紀錄。總務應能在同一張需求單看到受理、駁回、補資料、分流、工單同步、門市確認與門市回報問題等歷程。

總務可在需求詳情新增留言或備註。公開留言會顯示給門市端；內部備註只供總務端追蹤判斷依據與處理脈絡。

總務需求工作台詳情應以「下一步工作台」設計，而不是單純資料檢視。打開需求後，最上方需先顯示「目前要做什麼」的系統提示，依待受理、待總務複核、已受理 / 處理中、待門市確認等狀態自動說明下一步。受理、標記處理中、送門市確認等主要動作應集中在主要動作區；要求補資料、駁回、轉派等輔助動作放在其他處理區。後續處理方式、承辦角色、負責人與內部備註應與所選動作放在同一個操作區，避免總務或工務上下滑動尋找欄位。

工作台在桌機寬度足夠時，應將案件內容與處理動作分區呈現：列表用於選案，案件內容區顯示門市說明、營運影響、附件、處理紀錄與留言；動作區顯示目前可執行的受理、駁回、補資料、轉派與送門市確認。不得把案件內容、附件、處理紀錄、留言與所有動作硬塞在單一狹窄直式欄位，避免總務或工務在判斷案件時反覆上下滑動。

當總務在受理時選擇後續處理方式，系統需明確顯示該分流的後續承接模組：

1. 維修派工：建立或連結維修工單，後續回工單中心管理。
2. 添購 / 採購評估：進入採購評估，後續可延伸採購單、詢比議與請款。
3. 庫存出庫：進入庫存流向處理，需追蹤來源位置、出庫與目的門市收貨。
4. 調撥處理：進入調撥與收貨流程，需追蹤來源門市交出、運送方式與目的門市收貨。
5. 資產異動 / 門市配合：進入資產異動任務，包含位置、狀態、貼標、收回與報廢等配合作業。

因總務與工務未來會共用總務需求工作台，同一頁需依承辦角色提供判斷提示。總務視角著重採購、庫存、調撥、公開留言與內部備註；工務視角著重設備 / 設施位置、照片、保固、原廠或內部處理判斷。這些提示僅作為操作輔助，不取代正式分流欄位與權限控管。

### 4.2.1 待受理階段動作

門市送出統一需求單後，總務會在「總務需求工作台」的待受理狀態看到新需求。

總務在待受理階段需要支援以下動作：

1. 受理。
2. 駁回。
3. 要求門市補資料。
4. 轉派負責人。

#### 受理

總務接受需求，表示此需求會進入後續評估或處理流程。

總務按下受理時，必須已經判斷此需求的初步處理方向。因此受理時需要選擇分流方向，不提供「先受理，稍後判斷」作為正式狀態。

如果總務尚未判斷後續處理方式，需求應維持在待受理，而不是先受理。

受理時可選擇的初步分流方向包含：

1. 維修派工。
2. 添購 / 採購評估。
3. 庫存出庫。
4. 調撥處理。
5. 資產異動 / 門市配合。

#### 駁回

總務不處理此需求時，必須填寫駁回原因。駁回原因需顯示給門市端。

#### 要求門市補資料

當照片不清楚、描述不足、設備 / 設施主檔不正確，或總務需要更多資訊時，可要求門市補資料。

被要求補資料的需求，門市端需看到待補資料事項，並依總務要求回覆與上傳照片 / 附件。

補資料採用「補資料類型 + 補充說明」。

補資料類型包含：

1. 照片不清楚，請重新拍攝。
2. 缺少必要照片。
3. 問題描述不足。
4. 設備 / 設施選擇錯誤。
5. 數量 / 規格說明不足。
6. 其他。

總務可依補資料類型決定是否要求門市上傳照片 / 附件。也就是補資料時照片不一定永遠必填，而是依總務要求類型決定。

門市補資料完成後，需求不回到一般「待受理」，而是進入「待總務複核」狀態或工作台，讓總務確認補件內容是否足以繼續處理。

若總務複核通過，可繼續受理或分流。若補件仍不足，總務可再次要求補資料或駁回。

#### 轉派負責人

總務可將需求轉派給內部負責人。

未來公司總務職能會再區分為「總務」與「工務」，因此轉派不只是指定單一人員，也需要預留工作類型或承辦角色分流。

第一版至少需要記錄：

1. 承辦角色：總務 / 工務。
2. 負責人。
3. 轉派原因或說明。
4. 轉派時間。

### 4.2.2 受理時承辦角色與負責人

總務受理需求時，必須選擇承辦角色。

承辦角色第一版至少包含：

1. 總務。
2. 工務。

負責人欄位需要支援未來多人擴充，但第一版不一定要求使用者手動選擇。

目前總務與工務在組織架構上各只有一人，因此當某個承辦角色只有一位可負責人時，系統可自動帶入該負責人，不需要讓使用者選擇。

未來若同一承辦角色有多位可負責人，受理或轉派時應要求指定實際負責人。

規則如下：

1. 承辦角色必填。
2. 若承辦角色只有一位可負責人，負責人自動帶入。
3. 若承辦角色有多位可負責人，負責人必填。
4. 若承辦角色暫時沒有可負責人，系統應提示角色設定不完整，不能完成受理或轉派。

#### 合併重複需求

第一版暫不建立「合併重複需求」功能。

目前實務上尚未出現兩間門市需求需要合併處理的常見情境。若未來發生跨門市共同事件，例如區域性網路異常、同批設備瑕疵或同一供應商問題，再評估建立主要需求與子需求的合併機制。

### 4.3 添購申請處理結果

門市提出添購申請後，總務需要能記錄處理結果。

處理結果至少包含：

1. 核准。
2. 駁回。
3. 改由庫存出庫。
4. 改由其他門市或其他位置調撥。
5. 進入採購。

這些處理結果會影響後續流程：

1. 核准後，可繼續進入出庫、調撥或採購。
2. 駁回後，必須留下駁回原因並顯示給門市。
3. 改由庫存出庫時，需要建立庫存流向紀錄。
4. 改由調撥時，需要建立來源位置與目的門市的流向紀錄。
5. 進入採購時，才開始建立詢價、比價、議價、採購與請款相關紀錄。

### 4.3.1 維修派工流程

當需求被分流為「維修派工」時，流程如下：

1. 總務受理門市維修需求。
2. 總務確認需求已綁定設備 / 設施主檔。
3. 總務判斷承辦角色：總務 / 工務。
4. 總務選擇處理方式。
5. 總務視處理方式選擇廠商、原廠或內部處理人。
6. 總務可記錄詢價、報價、議價、維修費用與請款資訊。
7. 總務更新公開進度給門市。
8. 處理完成後，總務標記為待門市確認。
9. 門市確認完成後，案件正式完成。
10. 門市回報有問題時，案件回到總務處理中 / 待處理。

維修處理方式至少包含：

1. 內部自行處理。
2. 委外廠商處理。
3. 保固 / 原廠處理。
4. 暫不處理，改為觀察。

委外廠商處理時，需要能從供應商 / 廠商資料中選擇對應廠商。選擇廠商的目的不只是派工，也是為了讓系統能累積該廠商的處理紀錄，後續可用於品質、價格與速度評分。

保固內設備或設施應可選擇「保固 / 原廠處理」，並關聯原廠或保固服務廠商。

維修流程需要支援總務內部記錄報價與請款資訊，但門市端不需要看到報價、請款或內部議價細節。門市端只顯示公開處理進度與需要門市確認的事項。

「暫不處理，改為觀察」需要保留，用於輕微異音、偶發問題或總務判斷暫不需立即派工的情境。選擇此處理方式時，總務需填寫觀察原因與後續追蹤方式。

### 4.3.2 添購 / 採購評估流程

當需求被分流為「添購 / 採購評估」時，流程如下：

1. 總務受理添購 / 補充需求。
2. 總務判斷是否真的需要添購。
3. 總務選擇處理結果。
4. 若進入採購，總務選擇供應商 / 廠商。
5. 總務可記錄詢價、比價、議價。
6. 總務記錄核准數量與實際採購數量。
7. 採購完成後，可入庫到指定位置、指定門市，或直接送至門市。
8. 門市收到後進行收貨確認。
9. 門市確認收貨後，該需求可進入完成。

添購 / 採購評估的處理結果包含：

1. 駁回。
2. 改由庫存出庫。
3. 改由調撥。
4. 進入採購。
5. 改用替代品。

詢價、比價、議價不是每次採購都強制。無論金額大小，總務都可以依實務情況跳過詢比議直接採買。

若有執行詢比議，系統必須留下紀錄。後續系統需要能針對某個料件、設備或供應商快速查詢過往詢價、比價、議價紀錄。

採購完成後，貨品不一定要先進總部庫存。總務可選擇：

1. 入庫到總部或指定庫存位置。
2. 入庫到指定門市。
3. 直接送至門市。

若直接送至門市，系統仍應能記錄該品項流向與指定入庫門市，避免採購後的物品去向無法追蹤。

門市需要做收貨確認。收貨確認用來讓總務判斷此需求是否真的完成。

若總務改用替代品，不需要在系統中另開門市同意流程。實務上總務可能已用電話或通訊軟體與門市溝通，但系統上只需在採購或處理進度中備註替代品資訊，讓門市知道最後提供的品項與原需求不同。

### 4.3.3 庫存出庫流程

當需求被分流為「庫存出庫」時，流程如下：

1. 總務判斷門市需求可由既有庫存處理。
2. 總務選擇出庫來源：總部庫存、某門市庫存或其他庫存位置。
3. 總務選擇品項與出庫數量。
4. 若來源為門市，來源門市需要確認已交出。
5. 系統記錄來源庫存待移出或已移出。
6. 系統指定目的地：需求門市、部門、單位或其他位置。
7. 目的門市或目的單位收到後，需要做收貨確認。
8. 收貨確認後，才正式入到目的門市或目的位置庫存。
9. 收貨確認後，需求可進入完成。

出庫後一定要有收貨確認。若沒有收貨確認，系統只能知道總務建立了出庫紀錄，不能確認物品真的到達目的地，容易形成「空中單」。

若來源是其他門市，來源門市也需要確認已交出。門市端因此需要有一個「總務要求我交出 / 調出物品」的待處理事項。

庫存出庫的關鍵規則：

1. 來源可以是總部、門市或其他庫存位置。
2. 來源門市需要確認交出。
3. 目的門市需要確認收到。
4. 目的門市未確認收貨前，不應直接增加目的門市可用庫存。
5. 所有出庫與收貨確認都需要留下時間、人員與照片 / 附件紀錄。

料件庫存需要同時區分「庫存量」與「可用庫存量」。

1. 庫存量：代表該庫存位置已實際持有、已完成收貨或已確認存在的真實數量。
2. 可用庫存量：代表目前可被再次出庫、調撥、領用或承諾給其他需求的數量。

當料件從來源 A 移動到目的 B 的過程中，系統不應只用單一庫存數字表達。因為來源 A 已經交出後，該數量不應再被視為 A 可用；但目的 B 尚未確認收到前，也不能直接算入 B 的真實庫存量。

因此移動中的數量應採用以下規則：

1. 建立調撥 / 出庫單時：先保留調撥需求紀錄，不立即改變來源或目的庫存量；若系統支援預留量，則來源可用庫存量需扣除已預留數量。
2. 來源 A 確認交出時：來源 A 的可用庫存量先減少，並記錄該數量為移動中 / 待收貨。
3. 目的 B 尚未確認收貨前：目的 B 的庫存量與可用庫存量都不應增加。
4. 目的 B 收貨確認且數量正確時：目的 B 的庫存量正式增加，並同步增加可用庫存量。
5. 若目的 B 收貨數量不符或回報有問題：系統需保留差異原因、實收數量與照片 / 附件，不可直接把原調撥數量全數入庫。
6. 若調撥取消、退回或遺失，系統需保留來源交出、移動中、取消 / 異常的完整紀錄，並依實際結果調整庫存量與可用庫存量。

第一版若尚未建立獨立的預留量、移動中數量或異常差異表，至少需要在規格與 UI 上明確區分：

1. 帳面 / 真實庫存量。
2. 可用庫存量。
3. 移動中數量。
4. 待收貨數量。

避免使用者看到來源已交出但目的尚未收貨的料件時，誤以為兩邊都還能使用，或誤以為目的門市已經實際收到。

### 4.3.4 門市設備 / 料件的使用中與未使用狀態

門市擁有的設備與料件，和販售商品的庫存概念不同。

販售商品賣出後，庫存扣減代表商品已不在門市。但總務管理的設備與料件通常仍存在於門市，只是狀態不同。

因此門市設備 / 料件需要區分：

1. 使用中。
2. 未使用。
3. 待調出。
4. 待收貨。
5. 已報廢或停用。

例如某門市收到一整箱掛勾後，可能一開始全部登記成使用中。但總務從整體數據觀察，若該門市某款掛勾使用中數量明顯不合常理，總務可致電詢問門市是否其實有未使用數量。

若門市確認仍有未使用的某款掛勾，門市可回覆總務可調出數量。總務再依此建立調撥需求，將該料件調給提出需求的門市。

此流程代表系統需要支援：

1. 總務查看各門市某設備 / 料件的使用中與未使用數量。
2. 總務向門市確認未使用數量。
3. 門市回覆可調出數量。
4. 總務建立調撥需求。
5. 來源門市確認交出。
6. 目的門市確認收貨。

門市端也需要能看到總務要求自己處理的調出任務，而不只是自己提出的需求。

### 4.3.5 調撥處理流程

當需求被分流為「調撥處理」時，系統記錄的流程從總務已決定調撥來源後開始。

實務上，總務可能會先透過電話或通訊軟體詢問各門市是否有未使用數量。這個「確認未使用數量」階段第一版不需要用系統任務完成。

第一版調撥流程如下：

1. 門市提出需求，例如需要某款料件。
2. 總務查詢各門市 / 庫存位置的使用中與未使用狀態。
3. 總務用電話或其他方式確認可能來源門市是否可調出。
4. 若來源門市不可調出，總務自行尋找下一個可調撥來源。
5. 若全門市都無法調出，總務可改走添購 / 採購評估。
6. 總務確認來源後，在系統建立調撥需求。
7. 來源門市收到「請交出 / 調出」任務。
8. 來源門市確認已交出，並上傳照片。
9. 系統將該數量標記為運送中 / 待收貨。
10. 目的門市收到後確認收貨，並上傳照片。
11. 系統將該數量入到目的門市庫存。
12. 原需求進入待門市確認或已完成。

調撥過程中的庫存數量變化需符合「庫存量 / 可用庫存量」分離原則：

1. 來源 A 尚未確認交出前，來源 A 的庫存量維持不變；若調撥單已成立，來源 A 的可用庫存量應扣除已承諾調出的數量。
2. 來源 A 確認交出後，該數量進入移動中狀態，來源 A 不可再將該數量視為可用。
3. 目的 B 收貨前，目的 B 不得增加真實庫存量，也不得增加可用庫存量。
4. 目的 B 確認收到且數量正確後，才正式增加目的 B 的庫存量與可用庫存量。
5. 若目的 B 實收數量與調撥數量不同，需記錄差異數量與原因；系統不可用調撥單原數量直接覆蓋真實收貨結果。

調撥狀態至少包含：

1. 待來源門市交出。
2. 運送中 / 待目的門市收貨。
3. 已完成。
4. 已取消。

第一版不建立「待來源門市確認未使用數量」系統狀態。此確認由總務在系統外完成，系統只記錄已決定調撥後的正式調撥流程。

來源門市回覆可調出數量時，第一版不需要上傳照片，因為此步驟不作為正式系統任務。

來源門市確認已交出時，必須上傳照片。

目的門市確認已收貨時，必須上傳照片。

調撥需要記錄運送方式，第一版至少包含：

1. 總務自取。
2. 物流。
3. 人員帶回。

調撥流程的目的，是確保系統能追蹤物品從來源門市離開、運送中、到目的門市收貨入庫的完整流向，避免帳面調撥但實物狀態不明。

### 4.3.6 總務帳單管理

帳單管理不列入門市統一需求單第一版入口。門市端不需要建立帳單轉交需求。

水費、電費、電話費、網路費等帳單由總務自行追蹤未繳、登記與繳費狀態。

總務端帳單處理至少需要記錄：

1. 門市 / 單位。
2. 帳單類型：水費、電費、電話費、網路費、其他。
3. 計算起始日期。
4. 計算結束日期。
5. 帳單金額。
6. 繳費期限。
7. 是否已繳費。
8. 繳費日期。
9. 付款方式。
10. 收據 / 繳費證明附件。
11. 備註。
12. 是否異常。
13. 異常說明。

帳單不應只用單一「帳單月份」表示，因為各門市、各費用類型的計算區間可能不同。有些帳單是一個月，有些可能是兩個月或其他區間。

系統需要支援主管查詢某個月份各門市水費、電費、電話費等金額。查詢規則應以計算日期區間判斷：

> 只要帳單計算起始日期到計算結束日期有跨到查詢月份，就應在該月份查詢結果中顯示該筆帳單，並顯示金額與計算日期區間。

例如查詢 2026 年 8 月時，若某筆帳單計算區間為 2026-07-15 到 2026-09-14，該筆帳單需出現在 2026 年 8 月的查詢結果中。

帳單可標記異常金額。異常由總務自行判斷並填寫說明，例如金額明顯高於過往、疑似重複帳單、逾期或需追查。

繳費完成後需要上傳收據或繳費證明，以利事後查找與稽核。

帳單處理完成後不需要門市確認。後續繳費與紀錄由總務掌握。

### 4.3.7 資產異動 / 門市配合流程

資產異動 / 門市配合原則上由總務發起。

適用情境包含：

1. 新設備安裝。
2. 設備移入。
3. 設備移出。
4. 設備報廢。
5. 設備借用 / 轉移。
6. 盤點異常要求門市確認。
7. 總務要求門市拍照回覆。

第一版先支援上述異動類型。

基本流程如下：

1. 總務建立資產異動任務。
2. 總務指定門市、部門或單位。
3. 總務指定設備、設施或料件。
4. 總務指定門市要執行或確認的事項。
5. 門市執行後回覆並上傳照片。
6. 總務確認後，依情境更新資產狀態、位置或歸屬。

門市回覆資產異動時原則上需要上傳照片。

但實務上可能發生例外：總務已用電話或通訊軟體通知門市先把設備 / 料件轉回總部或送修，但總務尚未在系統發起任務，門市已經完成轉回，導致門市回系統確認時沒有現場照片可上傳。

此情境下，系統需允許走替代流程：

1. 門市標記已依總務指示完成，但無照片可上傳。
2. 門市填寫無照片原因。
3. 總務收到設備 / 料件時，由總務上傳收到時的照片。
4. 總務確認收到後，再更新資產狀態或位置。

資產狀態更新依情境決定：

1. 門市收到設備或料件時，門市確認收貨後可更新為目的門市持有、待使用或使用中。
2. 總務收到收回的設備或料件時，由總務確認收到後更新為總部持有、待維修、待報廢或其他狀態。
3. 採買備品入庫時，由總務確認入庫後更新庫存或資產狀態。
4. 若是門市配合拍照或盤點確認，需由總務複核後才更新正式資產資料。

此流程的設計重點是：資產狀態不能只因任務建立就自動改變，必須依實物確認點更新。

### 4.4 維修案件與設備 / 設施主檔

門市端建立維修 / 現場狀況需求時，不強制綁定設備或設施主檔。原因是門市實務上常見的入口不是「我要修哪一台設備」或「我要修哪一個設施」，而是「櫃台上方漏水」、「有鼠患」、「門鎖怪怪的」、「天花板滴水」這類現場狀況。

設備與設施主檔仍然重要，但主檔綁定責任應落在總務受理後的專業判斷。總務可在受理或派工前後，將需求補綁到既有設備 / 設施、建立新的主檔，或判斷此案不需要綁定資產。

門市端選擇維修標的時，不要求門市先分辨設備或設施。表單應提供單一搜尋入口，合併查詢該門市可維修的設備與設施。搜尋條件至少包含：

1. 設備編號 / 資產編號。
2. 條碼或標籤編號。
3. 設備 / 設施名稱。
4. 品牌、型號或規格。
5. 區域、放置位置或補充位置。

搜尋結果需清楚標示「設備」或「設施」，但這是系統辨識結果，不是要求門市先判斷。

此規則的目的：

1. 讓門市可以先快速回報現場問題。
2. 當能辨識出標的時，維修紀錄仍可回寫到正確資產。
3. 累積每個設備 / 設施的維修歷史。
4. 避免同一設備被門市用不同名稱重複回報。
5. 讓保固、廠商、請款與維修品質能被追蹤。

### 4.4.1 設備編號與貼標管理

設備與設施主檔都需要支援總務發起的編號與貼標管理。

總務應能針對每台設備建立或指定設備編號，也應能針對每個需要管理的設施建立或指定設施編號，並安排實體貼標。設備 / 設施編號的目的包含：

1. 讓門市能用設備 / 設施標號快速找到維修標的。
2. 降低同名設備、同區域設備或設施被選錯的機率。
3. 讓維修、保固、派工、請款與資產異動能回寫到同一台設備或同一個設施。
4. 方便日後盤點與資產清冊查找。

設備建立或補建時，除了設備本體照片外，也應支援「設備編號貼附位置照片」。此照片用來讓總務、工務、門市與廠商知道標籤貼在哪裡，避免報修或盤點時找不到標號。

設備主檔至少應支援以下圖片：

1. 設備本體照片。
2. 設備編號 / 標籤貼附位置照片。
3. 其他輔助照片，例如銘牌、序號、安裝位置。

設備編號設定、貼標任務、設備照片與貼附位置照片的建立，原則上由總務發起。門市可以配合拍照或回傳，但正式主檔更新需由總務確認。

設施也需要有設施編號。設施是否全面貼實體標籤需視實務可行性決定；第一版可先讓設施保留設施編號與位置描述，未來若特定設施適合貼標，需支援設施標籤照片與貼附位置照片。

初期資產建檔較接近「門市先用 Excel 回報現有設備清單，總務再建立正式設備主檔」的流程。Excel 不直接匯入系統暫存區，主要作為總務人工建檔與核對的依據。

第一版不採用設備範本流程。設備主檔由總務直接依門市、分類、品牌、型號、位置、設備照片與貼標位置照片建立；系統 UI 不顯示設備範本入口，也不在新增或編輯設備時要求套用範本。既有底層相容欄位或歷史資料可先保留，但不可成為總務日常操作入口。

料件通用性與相容性也不應依賴設備範本。第一版可先用品牌型號、廠商系列或總務備註描述某料件可用在哪些設備；未來若要更精準，應串接實際設備主檔或分類，而不是要求總務先建立另一套設備範本。

門市回傳 Excel 建議欄位：

1. 門市。
2. 樓層。
3. 區域。
4. 設備名稱。
5. 數量。
6. 品牌。
7. 型號。
8. 序號。
9. 設備狀態。
10. 備註。

門市不需要填寫設備分類、設備編號、QR Code、供應商、購買日期、請款資料與保固狀態。保固通常門市不知道或不可考，應由總務後續依實際資料補登。

門市回報的設備狀態只作為總務建檔參考，可簡化為：

1. 正常使用中。
2. 可用但少用。
3. 故障。
4. 停用。
5. 不確定。

位置第一版不要求過度精確，門市只需描述到樓層與區域。樓層可包含 `B1`、`1F`、`2F`、`3F`、其他；區域可包含櫃台內、櫃台外、倉庫、員工休息區、門口 / 騎樓、其他。

總務依 Excel 建立正式設備主檔後，門市再依設備編號進系統補傳照片。需要補傳的照片至少包含：

1. 設備本體照片。
2. 設備標籤貼附位置照片。

這個流程不只適用初期大量建檔。未來若總務採購設備並直接請廠商寄到門市，也可由總務先建立正式設備主檔，設備進入待補照片與待貼標流程；門市收到設備後補設備照片，總務列印 QR 標籤轉交門市，門市貼標後上傳標籤位置照片，最後由總務複核完成。

設備主檔除了設備使用狀態外，需另外追蹤建檔 / 貼標狀態。第一版建議狀態包含：

1. 待上傳設備照片。
2. 待貼標照片。
3. 待總務複核。
4. 已完成。

建檔 / 貼標狀態代表導入工程與照片追蹤進度，不等同設備是否故障或是否仍在使用。設備使用狀態仍使用原本的使用中、備品、暫停使用、退役、報廢等狀態。

門市端配合補設備照片或貼標位置照片時，應整合到「我的追蹤」而不是另開獨立入口。因為這類事項不是門市主動提出的回報，而是總務發起、門市配合完成的待辦；在「我的追蹤」中資料狀態可歸類於待補資料，但門市端篩選卡與任務標籤應顯示為「待我處理」，並在狀態篩選卡顯示件數。「我的追蹤」預設應選取「待我處理」，讓店長優先看到自己需要回覆、確認或上傳照片的事項。

門市端待補照片卡片需以現場可核對資訊為主，不需呈現設備列表的完整主檔明細。至少顯示：

1. 待辦類型：待上傳設備照片或待上傳貼標照片。
2. 設備名稱。
3. 設備編號。
4. 所屬門市。
5. 位置：樓層 / 區域或簡短位置描述。
6. 目前建檔 / 貼標進度條。

點開待補照片任務後，右側詳情仍以簡化操作為原則，只提供現場人員上傳所需資訊、現有設備照片預覽、上傳照片按鈕與任務說明。上傳完成後由系統依照片用途自動推進下一個建檔 / 貼標狀態，不需門市手動選狀態。

門市上傳貼標位置照片後，設備不可直接視為完成建檔，必須進入「待總務複核」。總務需在設備主檔詳情完成以下任一動作：

1. 照片正確，完成建檔：設備建檔 / 貼標狀態改為已完成，並記錄複核時間、複核人員與可選填說明。
2. 退回重拍：總務必須填寫退回原因，且退回重拍時需選擇退回範圍，可只退回設備照片、只退回貼標位置照片，或兩者都退回；門市端「我的追蹤」的待我處理需顯示此退回原因，讓門市知道要重拍的問題。

若總務只退回設備照片，門市補完設備照片後，系統不可強迫重傳貼標位置照片，需直接回到待總務複核。若總務只退回貼標位置照片，門市補完貼標位置照片後，直接回到待總務複核。若兩者都退回，門市需依序完成設備照片與貼標位置照片，最後才回到待總務複核。

若設備貼標照片被總務退回重拍，門市端「我的追蹤」不只在詳情顯示退回原因，列表卡片也需顯示退回原因摘要，讓店長在待我處理清單中能先判斷要重拍哪一台設備與原因。

未來系統需支援從設備 / 設施主檔列印標籤紙。標籤紙至少需包含：

1. 設備編號或設施編號。
2. QR Code。
3. 必要時可加上設備 / 設施名稱或簡短識別文字。

標籤紙不應列印門市代碼或固定門市資訊，避免設備 / 設施調撥或移轉後需要重新貼標。

第一版設備 QR 標籤列印規格先採最大 `60 x 25 mm`。若以 300dpi 輸出，對應像素約為 `709 x 295 px`。實務耗材建議為霧面白色 PET、強黏膠、黑色全樹脂抗刮碳帶，以提高門市環境中的耐刮、耐水與黏著穩定性。列印版面需避免把 QR Code 壓得過小；60 x 25 mm 標籤中 QR Code 建議保留約 19 mm 正方形，旁邊顯示設備 / 設施編號與名稱。

QR Code 掃描後應開啟對應設備 / 設施的查詢頁。掃描者必須先完成系統登入，且需具備有效系統帳號，才能看到資產資訊；未登入時應導向登入頁，登入完成後回到原 QR 掃描頁。QR 掃描 API 不得對未登入請求回傳設備 / 設施資料。

QR Code 掃描頁需要依登入帳號的 RBAC 權限與資料範圍顯示不同資訊。

1. 門市人員 / 店長：可查看自己門市或自己被指派範圍內的設備 / 設施公開資訊、目前使用門市、位置、照片、維修回報入口、維修紀錄摘要與保固狀態。
2. 總務 / 工務：可查看所有設備 / 設施公開資訊，並可從掃描頁進入系統內完整資產詳情。
3. 主管 / 管理者：第一版以查看與追蹤為主，可查看資產公開資訊、歸屬、位置、維修紀錄摘要與保固狀態。
4. 系統管理員：可查看完整資訊並進入所有管理功能。

掃描頁不應把供應商、請款、完整資產異動、調撥紀錄等內部管理資料直接公開給所有登入者。若總務需要查看完整細節，應從掃描頁提供返回系統內單一設備 / 設施詳情的入口，並由該詳情頁依權限控管。

門市人員使用手機掃描並登入後，至少需要能看到：

1. 設備 / 設施基本資訊。
2. 設備編號或設施編號。
3. 設備 / 設施名稱、品牌、型號或規格。
4. 目前由總務服務中心管理紀錄中的使用門市。
5. 放置區域或位置描述。
6. 目前資產狀態或使用狀態。
7. 可供門市辨識的照片。

QR Code 查詢頁的目的，是讓門市不需要先記住設備屬於設備或設施，也不需要手動搜尋，就能快速確認掃描到的標的是哪一個資產，以及目前系統認定此設備 / 設施歸屬或使用於哪間門市。

設備 / 設施主檔建立時，系統即應建立一組長期有效的 QR token 與穩定掃描入口。QR token 不應由前端手動指定，也不應直接使用維修表單路由、門市、位置或狀態作為 QR Code 內容。新增設備 / 設施完成後，系統需能回傳此資產的 QR 掃描入口，供後續標籤列印流程使用。

QR Code 掃描入口的路由應保持穩定，例如 `/general-affairs/assets/scan/{qrToken}`。此入口負責解析 token 對應的設備 / 設施，並即時顯示目前規格定義的資訊。未來若掃描頁顯示內容、維修回報入口或前端流程調整，只需修改掃描入口頁與後端解析邏輯，不需重新製作既有 QR Code 標籤。

QR token 管理原則：

1. 一般情況下 QR token 長期有效，不因門市、位置、狀態、負責人或維修入口調整而重做。
2. 設備 / 設施走到報廢狀態時，系統應自動停用該 QR token，掃描後不得再進入一般資產資訊頁。
3. 報廢後掃描舊 QR Code 時，系統可顯示「此設備 / 設施已報廢或停用」的安全提示，但不提供維修回報入口。
4. 第一版不建立掃描紀錄，不記錄誰在什麼時間掃描哪個 QR Code。
5. 第一版不建立標籤補印流程或補印狀態管理。總務可依實際狀況從設備 / 設施列表重新列印 QR 標籤。

### 4.4.2 資產保固管理

設備 / 設施主檔需要支援保固資訊管理。第一版保固管理不需要做成完整合約管理系統，但需要能讓總務在查詢單一設備 / 設施時快速知道是否仍在保固內、保固如何查詢，以及需要使用哪些證明或帳號資料。

保固狀態至少包含：

1. 無保固。
2. 有保固。

當資產標記為有保固時，至少需要記錄：

1. 保固開始日。
2. 保固到期日。
3. 保固來源：紙本 / 附件、線上登錄、廠商代登錄、原廠登錄、其他。
4. 保固說明或注意事項。
5. 保固附件。

保固附件可包含：

1. 保固卡照片。
2. 發票 / 收據。
3. 購買證明。
4. 原廠或供應商保固書 PDF。
5. 線上登錄完成截圖。
6. 登錄成功確認信或通知截圖。

線上登錄型保固需要支援以下欄位：

1. 登錄平台名稱。
2. 登錄網址。
3. 登錄日期。
4. 登錄帳號或登錄信箱。
5. 登錄密碼。
6. 保固查詢網址。
7. 登錄完成證明附件。
8. 備註，例如使用總務信箱登錄、由廠商協助登錄、或查詢時需要序號。

登錄密碼屬於敏感資訊，第一版允許保存，但必須符合以下規則：

1. 不得以明碼儲存在資料庫。
2. 必須由 server-side 加密後保存。
3. 前端一般列表、掃描頁、門市端與主管查看頁不得直接顯示密碼。
4. 只有具備保固敏感資訊查看權限的總務、系統管理員或被明確授權者可以查看。
5. 密碼預設以遮蔽形式顯示，例如 `********`。
6. 使用者需按「查看密碼」才可解密顯示。
7. 每次查看密碼都必須留下稽核紀錄。
8. 稽核紀錄至少包含查看人、查看時間、資產類型、資產 ID、保固資料 ID、IP 或 request metadata、查看原因或操作來源。
9. 密碼更新時需記錄更新人與更新時間，但不記錄舊密碼明文。

保固敏感資訊權限需獨立於一般設備 / 設施查看權限。具備設備查看權限者可以知道保固狀態與到期日，但不代表可以查看保固登錄密碼。

建議第一版新增或預留以下 permission codes：

1. `general_affairs.warranty.view`：查看保固基本資訊。
2. `general_affairs.warranty.manage`：建立與更新保固資料。
3. `general_affairs.warranty.secret.view`：查看保固登錄密碼等敏感資訊。
4. `general_affairs.warranty.secret.audit`：查看敏感資訊查看紀錄。

保固紀錄應跟著設備 / 設施主檔走，不因設備移轉門市而斷掉。維修派工時若資產仍在保固內，系統應提醒總務可優先選擇保固 / 原廠處理。

### 4.4.3 單位 / 部門資產列表

總務未來需要能列出各單位、各部門與各門市的資產列表。

因此設備 / 設施主檔不能只支援門市資產，也需要支援總部單位、部門或其他內部組織的資產歸屬。

資產主檔至少需要能記錄：

1. 資產歸屬類型：門市 / 部門 / 單位 / 其他。
2. 歸屬門市、部門或單位。
3. 實際放置位置。
4. 使用或保管負責人。
5. 資產狀態。
6. 資產分類。
7. 品牌、型號、規格。
8. 資產編號。
9. 保固資訊。
10. 關聯廠商或供應商。
11. 維修與異動紀錄。

系統後續應支援總務依以下條件查詢資產：

1. 依門市查詢。
2. 依部門查詢。
3. 依單位查詢。
4. 依資產分類查詢。
5. 依資產狀態查詢。
6. 依保管人或負責人查詢。

此能力會影響未來資料模型設計：資產主檔應以「組織歸屬」作為彈性欄位，而不是只能綁定 store。

### 4.5 採購 / 派工後的詢比議與請款

詢價、比價、議價與請款紀錄不是每張門市需求一建立就產生。

只有當總務決定需求進入採購或派工後，才建立相關紀錄。

總務需要能記錄：

1. 詢價廠商。
2. 報價金額。
3. 報價內容。
4. 比價紀錄。
5. 議價結果。
6. 最終選定廠商。
7. 選擇原因。
8. 請款項目。
9. 請款金額。
10. 發票、收據或其他請款附件。
11. 付款狀態。

系統需保留總務記錄詢比議過程的能力，即使最後不一定進入正式採購或派工，也應能留下評估紀錄。

### 4.6 供應商 / 廠商管理

總務需要能在系統中完整建立與維護供應商 / 廠商資料。

廠商資料至少包含：

1. 基本資料。
2. 聯絡資訊。
3. 服務區域。
4. 服務內容。
5. 販售品項。
6. 價格資訊。
7. 合作紀錄。
8. 維修品質紀錄。
9. 價格合理度紀錄。
10. 處理速度紀錄。
11. 配合度紀錄。

供應商 / 廠商管理不只是通訊錄，而是總務做詢比議、派工、採購與品質評估的資料基礎。

### 4.7 料件通用性 / 相容性

總務需要能透過系統建立料件與設備之間的通用性或相容性。

例如：

1. A 牌中島架可使用哪些層板。
2. A 牌中島架可使用哪些掛勾。
3. 某品牌設備可使用哪些替代料件。
4. 某料件可同時適用哪些設備或設施。

料件相容性資料的用途：

1. 門市提出需求時，降低選錯料件的機率。
2. 總務判斷出庫、調撥或採購時，可快速確認可用料件。
3. 庫存管理能知道哪些料件可替代使用。
4. 採購時可比較不同供應商或不同品牌的相容料件。

相容性應由總務管理，不應由門市自由建立。

## 5. 共用資料模型與流程

### 5.1 核心設計決策：統一總務需求單

門市端不應被要求精準判斷自己現在屬於哪一種總務流程。

對門市來說，實務情境通常只是：

1. 東西壞了。
2. 東西不夠。
3. 需要添購。
4. 總務要求我配合某件事。
5. 我想知道目前處理到哪。

要求門市一開始就聰明區分「維修、採購、料件、調撥、庫存、資產異動」會增加使用難度，也容易造成分類錯誤。

因此系統採用「統一總務需求單」作為門市端入口。

門市端先建立一張需求單，描述自己遇到的狀況或需要的事項。總務受理後，再由總務端判斷並分流到正確後續流程。

### 5.2 門市端需求單

門市建立需求單時，不需要理解總務後台完整分類。

表單應以門市容易理解的問題引導，例如：

1. 我要回報設備 / 設施問題。
2. 我要申請添購。
3. 我要申請料件 / 耗材。
4. 我要回覆總務要求我配合的事項。

這些選項只是門市端的初步描述，不直接等於最終處理流程。

需求單至少包含：

1. 門市。
2. 需求主旨。
3. 初步需求類型。
4. 問題或需求描述。
5. 急迫程度。
6. 聯絡人與聯絡方式。
7. 照片或附件。
8. 是否關聯既有設備 / 設施 / 料件。
9. 建立人。
10. 建立時間。

其中維修 / 現場狀況類需求不強制選擇既有設備或設施主檔。若門市知道設備編號或名稱，可以協助帶入；若不知道，仍可直接描述現場狀況並上傳照片，由總務受理後再判斷是否需要補建或補綁設備 / 設施主檔。

### 5.2.1 門市表單第一題

門市建立需求單時，第一題使用情境式問題：

> 你想處理什麼事情？

選項包含：

1. 東西壞了，需要維修。
2. 東西不夠，需要添購 / 補充。
3. 總務要求我回覆 / 確認。

這些選項用來引導門市填寫資料，不代表最終處理流程。最終流程仍由總務受理後分流。

第一版不提供「其他」入口。原因是目前門市需求已限縮為明確且可處理的分類，且添購 / 補充流程已能承接公司目前尚未建立主檔的設備、設施、料件或庶務用品需求。

若門市遇到不在四類入口中的情境，應先與總務確認，由總務判斷是否補建主檔、改走既有入口，或未來再新增正式需求類型。

### 5.2.2 維修需求欄位

當門市選擇「東西壞了，需要維修」時，表單至少包含：

1. 門市。
2. 問題類型：設備故障、店內設施 / 環境問題，或不確定請總務判斷。
3. 若為店內設施 / 環境問題，再選擇現場狀況類型。
4. 發生地點 / 補充位置。
5. 問題描述。
6. 已知道設備編號、條碼、名稱、品牌型號或位置時，可選填搜尋既有設備 / 設施主檔。
7. 對營運的影響可用快速勾選，例如影響收銀、影響營業、影響顧客動線、安全疑慮、影響門市作業或目前仍可正常使用。
8. 聯絡人。
9. 聯絡電話。
10. 照片 / 附件。
11. 備註。

維修標的搜尋是選填輔助，不是門市送出門檻。系統需要避免讓門市為了送單而猜測設備或設施分類。設備故障分流才讓門市可直接輸入設備編號或設備名稱；店內設施 / 環境分流不顯示設備選擇器，只顯示漏水、病媒、門鎖等現場狀況按鈕與位置欄位。

維修需求必須上傳照片。照片是總務判斷問題、與廠商溝通、後續比對完成結果的重要依據。

門市不選擇急迫程度。原因是若開放門市自行選擇，一線使用者容易全部選緊急，導致總務無法有效排序。

門市端可改為描述影響狀況，例如：

1. 是否影響營業。
2. 是否完全無法使用。
3. 是否有安全疑慮。
4. 是否仍可暫時使用。
5. 是否已有臨時處理方式。

急迫程度由總務受理時判斷與設定。

### 5.2.3 添購 / 補充需求欄位

當門市選擇「東西不夠，需要添購 / 補充」時，表單至少包含：

1. 門市。
2. 缺東西 / 想補充的情境，例如陳列架不夠用、掛勾 / 層板 / 配件不足、包材 / 清潔用品不足、設備配件遺失或損壞、門市需要新增用品、不知道分類請總務判斷。
3. 希望補充的品項名稱。
4. 初步分類：不確定請總務判斷、料件、庶務用品。
5. 門市希望數量。
6. 使用位置。
7. 用途說明。
8. 希望規格。
9. 已知道料件名稱、料號或規格時，可選填搜尋既有料件主檔。
10. 照片 / 參考圖片。
11. 備註。

料件主檔搜尋是選填輔助，不是門市送出門檻。門市不需要先判斷總務後續要採庫存出庫、其他門市調撥、重新採購或替代料件；這些由總務受理後判斷。

添購 / 補充需求必須上傳照片或參考圖。原因是門市可能申請公司目前沒有建立主檔、沒有標準品名，或不容易用文字描述的品項。

門市可以填寫希望規格，但最終品牌、型號、採購品項與供應商由總務判斷。

門市需要填寫希望數量，但最終核准數量、採購數量、出庫數量或調撥數量由總務判斷。

總務受理後可將此類需求分流為：

1. 駁回。
2. 改由庫存出庫。
3. 改由調撥。
4. 進入採購。
5. 改用替代品項。

### 5.2.4 總務要求回覆 / 確認

「總務要求我回覆 / 確認」不是門市自由新增的需求類型，而是由總務端發起。

適用情境包含：

1. 維修完成確認。
2. 收貨確認。
3. 資產移入 / 移出確認。
4. 補照片。
5. 補資料。
6. 依總務要求執行某件事後回報。

門市端只會看到總務指派給門市的待回覆事項，並針對該事項回覆。

門市回覆欄位至少包含：

1. 回覆結果：已完成 / 有問題 / 無法執行。
2. 回覆說明。
3. 照片 / 附件。
4. 回覆人。
5. 回覆時間。

門市回覆時原則上都需要附照片。照片可降低雙方對完成結果、收貨狀態或資產異動結果的認知落差。

如果門市選擇「有問題」，必須填寫問題原因並上傳照片。系統應自動將該需求或任務退回總務的處理中 / 待處理工作台，讓總務重新處理。

### 5.2.6 導入風險：未在系統發起回覆事項

初期雙方尚未熟悉系統流程時，可能發生以下情況：

1. 總務以電話或通訊軟體告知門市要配合某件事。
2. 但總務沒有在系統中發起「待門市回覆 / 確認」事項。
3. 門市回到系統後找不到可填寫或確認的任務。

因此系統導入時需要明確規範：

1. 需要門市回覆、確認、補件或拍照的事項，總務必須在系統中建立待回覆事項。
2. 門市原則上只針對系統中的待回覆事項進行回覆。
3. 若門市接到電話通知但系統沒有任務，應回報總務補建任務後再填寫。

這是上線教育與流程落地的重點，不只是系統功能問題。

### 5.3 總務端分流

總務受理需求單後，決定後續處理方式。

一張需求單可被分流為：

1. 維修工單。
2. 採購流程。
3. 庫存出庫。
4. 門市 / 倉庫 / 位置調撥。
5. 資產異動任務。
6. 駁回。
8. 其他總務處理紀錄。

分流時總務需要記錄：

1. 是否受理。
2. 分流類型。
3. 處理說明。
4. 負責人。
5. 預計處理時間。
6. 是否需門市補件或配合。
7. 是否公開給門市。
8. 若駁回，必填駁回原因。

### 5.4 需求單與後續單據關係

統一需求單是門市端追蹤入口，後續流程則是總務端專業處理紀錄。

關係如下：

1. 一張需求單可以沒有後續單據，例如被駁回或只需簡單回覆。
2. 一張需求單可以產生一張維修工單。
3. 一張需求單可以產生一張採購紀錄。
4. 一張需求單可以產生一筆或多筆庫存出庫 / 調撥紀錄。
5. 一張需求單可以產生資產異動任務。
6. 一張需求單後續可能產生詢比議與請款紀錄。

門市端仍只需要回到需求單查看進度，不需要知道後台實際產生了多少管理單據。

### 5.5 統一狀態與公開進度

需求單需要有門市可理解的統一狀態：

1. 待受理。
2. 待補資料。
3. 待總務複核。
4. 已受理。
5. 處理中。
6. 待門市確認。
7. 已完成。
8. 已駁回。
9. 已取消。

這 9 個是門市可見主狀態。主狀態定義如下：

1. 待受理：門市已送出，總務尚未受理。
2. 待補資料：總務要求門市補資料。
3. 待總務複核：門市已補資料，等待總務確認補件是否足夠。
4. 已受理：總務已接受需求，並已決定初步處理方向。
5. 處理中：總務正在處理，可能是派工、採購、出庫、調撥或資產異動。
6. 待門市確認：總務認為已處理完成，等待門市確認結果。
7. 已完成：門市確認完成，或不需門市確認的流程由總務完成。
8. 已駁回：總務不受理或不處理，並提供原因。
9. 已取消：因特殊原因取消，例如門市撤回、需求不存在或流程中止。

總務端可以有更細的內部狀態，但門市端只顯示經整理後的公開狀態與公開進度。

### 5.5.1 總務內部分流狀態

總務端可依分流方向使用更細的內部狀態。這些狀態主要供總務工作台、篩選與內部追蹤使用，不一定全部顯示給門市。

#### 維修內部狀態

1. 待派工。
2. 內部處理中。
3. 廠商處理中。
4. 保固 / 原廠處理中。
5. 觀察中。
6. 待門市確認。
7. 已完成。
8. 已取消。

#### 添購 / 採購內部狀態

1. 評估中。
2. 改由庫存出庫。
3. 改由調撥。
4. 採購中。
5. 待收貨。
6. 已完成。
7. 已駁回。
8. 已取消。

#### 共用物品流向狀態

庫存出庫與調撥共用同一套物品流向狀態。

原因是兩者本質上都是物品從來源位置流向目的位置，差別只在來源與目的地的類型。

共用物品流向狀態包含：

1. 待來源確認交出。
2. 運送中 / 待目的地收貨。
3. 已收貨。
4. 已完成。
5. 已取消。

此狀態適用於：

1. 總部出庫到門市。
2. 門市調撥到門市。
3. 門市調回總部。
4. 總部或門市流向部門 / 單位。
5. 其他庫存位置之間的移動。

#### 帳單內部狀態

1. 待總務收件。
2. 待登記。
3. 待繳費。
4. 已繳費。
5. 異常追蹤中。
6. 已完成。
7. 已取消。

#### 資產異動內部狀態

1. 待門市執行。
2. 待總務收到。
3. 待總務複核。
4. 已更新資產狀態。
5. 已完成。
6. 已取消。

每次總務更新進度時，需要區分：

1. 公開進度：門市可見。
2. 內部備註：僅總務可見。

公開進度原則上由系統依流程節點自動產生，不要求總務每次手動填寫。

例如：

1. 總務受理並選擇維修派工後，系統可顯示「總務已受理，進入維修派工」。
2. 總務選擇廠商處理後，系統可顯示「已安排廠商處理」。
3. 總務建立調撥後，系統可顯示「已建立調撥，等待來源門市交出」。
4. 來源門市確認交出後，系統可顯示「物品已交出，等待目的門市收貨」。
5. 總務標記待門市確認後，系統可顯示「總務已完成處理，等待門市確認」。

系統自動進度的目的，是讓門市能穩定看到處理節點，不因總務忘記手動更新而失去追蹤感。

內部備註為選填，僅總務 / 工務可見。

門市端可以在需求進度中留言回覆。門市留言用於補充現場狀況、詢問進度或回報變化，不一定會直接改變需求狀態。

若門市留言內容需要總務處理，總務端應能在工作台看到有新留言或未讀回覆。

### 5.5.2 留言 / 溝通紀錄

每張需求單需要有留言與溝通紀錄。

留言類型包含：

1. 門市留言。
2. 總務公開回覆。
3. 總務 / 工務內部備註。
4. 系統自動紀錄。

門市端看得到：

1. 自己與同門市相關留言。
2. 總務公開回覆。
3. 系統自動公開進度。

門市端看不到：

1. 總務 / 工務內部備註。
2. 報價、請款、議價內容。
3. 廠商評分。
4. 其他標示為內部可見的紀錄。

附件規則：

1. 門市留言可以附照片 / 附件。
2. 總務公開回覆可以附照片 / 附件。
3. 內部備註也可以附附件。
4. 留言附件需繼承留言可見性：公開留言附件門市與總務可見，內部備註附件僅總務 / 工務可見。

未讀規則：

1. 有新門市留言時，總務端顯示未讀或待回覆提示。
2. 有總務公開回覆時，門市端顯示未讀提示。

第一版總務工作台先實作案件層級的「門市待回覆」提示：若同一張需求單最後一則門市公開留言晚於最後一則總務公開回覆或公開處理事件，則在總務需求工作台列表與詳情中標示待回覆。此判斷不等同完整逐人已讀紀錄；未來若需要精準到每位使用者，再新增 read receipt 設計。

留言允許編輯與刪除。

但由於總務需求、維修、採購、調撥與請款可能產生責任歸屬，系統後續設計應保留留言編輯與刪除紀錄，例如：

1. 原始內容。
2. 編輯後內容。
3. 編輯人。
4. 編輯時間。
5. 刪除人。
6. 刪除時間。

第一版若尚未實作完整稽核，也應避免真正硬刪除重要留言，優先採軟刪除或保留異動紀錄。

### 5.6 設計原則

此設計的核心原則：

1. 門市端簡化：門市只提出需求，不負責專業分流。
2. 總務端專業化：由總務判斷受理、分流與處理方式。
3. 追蹤一致：門市所有需求都回到同一個進度列表。
4. 後台可擴充：總務端可逐步增加維修、採購、庫存、調撥、帳單、請款與廠商評估功能。
5. 紀錄可追溯：所有後續單據都能追溯回原始需求單。

## 6. 測試區補強方向

### 6.1 第一階段：核心流程骨架

第一階段目標是讓門市能提出需求，總務能受理、分流、追蹤，先把主流程跑通。

第一階段包含：

1. 統一總務需求單。
   - 維修需求。
   - 添購 / 補充需求。
   - 門市留言 / 附件。
   - 門市進度查詢。
2. 總務待受理工作台。
   - 受理。
   - 駁回。
   - 要求補資料。
   - 轉派總務 / 工務。
3. 受理分流。
   - 維修派工。
   - 添購 / 採購評估。
   - 庫存出庫。
   - 調撥處理。
   - 資產異動 / 門市配合。
4. 門市可見主狀態。
   - 待受理。
   - 待補資料。
   - 待總務複核。
   - 已受理。
   - 處理中。
   - 待門市確認。
   - 已完成。
   - 已駁回。
   - 已取消。
5. 門市確認。
   - 維修完成確認。
   - 收貨確認。
   - 有問題退回總務處理。
6. 共用物品流向。
   - 來源確認交出。
   - 運送中 / 待收貨。
   - 目的地收貨確認。

### 6.2 第二階段：總務管理能力補強

第二階段目標是讓總務能更完整管理資產、廠商、採購、庫存。

第二階段包含：

1. 設備 / 設施主檔完整化。
2. 門市 / 部門 / 單位資產。
3. 使用中 / 未使用 / 待調出 / 待收貨。
4. 料件主檔與相容性。
5. 供應商 / 廠商管理。
6. 採購與詢比議。
7. 請款與附件。

### 6.3 第三階段：帳單、報表與管理追蹤

第三階段目標是提供主管與管理層需要的追蹤與分析。

第三階段包含：

1. 總務帳單管理。
2. 月份帳單查詢。
3. 門市費用比較。
4. 廠商品質比較。
5. 維修頻率。
6. 採購金額。
7. 庫存流向。
8. 主管工作台。

### 6.4 未來保留

1. 跨門市重複需求合併。
2. 主管高金額 / 高風險核准。
3. 更完整稽核版本控管。
4. 自動異常偵測。
5. 供應商自動評分模型。

## 7. 角色與權限

### 7.1 RBAC 設定原則

系統不應假設固定角色名稱自動擁有權限。

既有系統中已存在店長等角色，實際角色與權限勾選由管理者在 RBAC 後台設定。本規格書只定義各角色視角建議應具備的 permission codes，供後續設定與開發對齊。

### 7.2 門市人員 / 店長

#### 可執行能力

門市人員 / 店長可以：

1. 建立總務需求單：維修需求、添購 / 補充需求。
2. 查看自己門市的總務需求，包含自己建立與同門市其他人建立的需求。
3. 依總務要求補資料，包含照片、附件與說明。
4. 在自己門市需求單中留言，並可附照片 / 附件。
5. 編輯 / 刪除自己的留言。
6. 確認完成，包含維修完成確認、收貨確認、資產異動配合確認。
7. 回覆總務指派事項，包含確認交出、確認收貨、拍照回覆、補資料、回覆有問題或無法執行。
8. 查看自己門市資產 / 料件，包含使用中、未使用、待調出、待收貨。
9. 查看自己門市的物品流向任務，包含總務要求交出、待收貨與已完成紀錄。

門市人員 / 店長不可以：

1. 查看其他門市需求，除非自己門市是調撥來源或目的門市。
2. 修改總務分流結果。
3. 修改總務內部狀態。
4. 查看內部備註。
5. 查看報價、請款、議價。
6. 查看廠商評分。
7. 自行建立資產異動任務。
8. 自行修改正式資產主檔。
9. 自行修改正式庫存帳。
10. 自行把使用中 / 未使用數量改成正式庫存結果，除非是總務指派的確認任務。

#### RBAC 權限代碼

各角色建議勾選的 permission codes 會在整份規格書確認完成後，再統一整理成「RBAC 權限代碼建議表」。

### 7.3 總務角色

#### 可執行能力

總務可以：

1. 查看所有總務需求單。
2. 受理需求。
3. 駁回需求並填寫原因。
4. 要求門市補資料。
5. 轉派承辦角色：總務 / 工務。
6. 處理添購 / 採購評估。
7. 建立採購紀錄。
8. 記錄詢價、比價、議價。
9. 建立庫存出庫。
10. 建立調撥需求。
11. 建立資產異動 / 門市配合任務。
12. 管理庶務 / 料件庫存。
13. 管理供應商 / 廠商資料。
14. 記錄報價、請款、發票、收據。
15. 管理帳單與繳費狀態。
16. 查看內部備註。
17. 新增內部備註。
18. 查看廠商評分與合作紀錄。
19. 查看各門市、部門、單位資產列表。
20. 查看報表與異常提醒。

#### 不一定可執行能力

以下能力不預設所有總務都可以執行，需依公司管理規則與 RBAC 設定決定：

1. 系統管理 / RBAC 設定。
2. 刪除正式主檔。
3. 修改已完成 / 已請款紀錄。
4. 直接修改所有歷史紀錄。

### 7.4 工務角色

#### 可執行能力

工務可以：

1. 查看分派給工務的需求 / 工單。
2. 查看維修類需求。
3. 更新維修處理狀態。
4. 新增維修處理紀錄。
5. 上傳維修照片 / 附件。
6. 新增內部備註。
7. 建立或更新設備 / 設施維修紀錄。
8. 查看設備 / 設施主檔。
9. 查看設備 / 設施維修歷史。
10. 協助判斷是否需廠商、原廠或保固處理。
11. 標記處理完成，送門市確認。
12. 回覆門市留言。

#### 不預設可執行能力

以下能力不預設工務可執行，除非另行授權：

1. 建立採購。
2. 管理供應商基本資料。
3. 記錄請款、發票、收據。
4. 管理帳單。
5. 修改庫存帳。
6. 系統管理 / RBAC。
7. 查看非維修相關財務資訊。

### 7.5 主管 / 管理者

第一版主管 / 管理者定位為查看與追蹤，不負責在系統內核准、修改或直接執行總務作業。

#### 可執行能力

主管 / 管理者可以：

1. 查看所有總務需求。
2. 查看所有門市、部門、單位資產。
3. 查看總務 / 工務工作量與處理進度。
4. 查看逾期、待處理、異常案件。
5. 查看廠商評分與合作紀錄。
6. 查看詢價、比價、議價紀錄。
7. 查看請款、帳單、繳費狀態。
8. 查看水費、電費、電話費月查詢與異常金額。
9. 查看庫存與流向。
10. 查看報表。

#### 不預設可執行能力

以下能力第一版不預設開放給主管 / 管理者：

1. 直接修改需求單。
2. 直接修改庫存。
3. 直接修改請款 / 帳單。
4. 直接刪除資料。
5. 系統管理 / RBAC 設定，除非兼具系統管理員權限。
6. 核准或退回高風險 / 高金額事項。

若未來公司需要主管核准流程，可在第二階段再加入核准 / 退回功能。

### 7.6 系統管理員

系統管理員在總務服務中心具備全開權限。

系統管理員可以：

1. 查看、建立、更新與管理所有總務需求。
2. 查看、建立、更新與管理所有維修、採購、出庫、調撥、帳單、資產異動流程。
3. 查看與管理所有門市、部門、單位資產。
4. 查看與管理所有庫存與物品流向。
5. 查看與管理所有供應商 / 廠商資料。
6. 查看與管理所有詢價、比價、議價、請款、發票、收據與帳單紀錄。
7. 查看公開進度、內部備註、留言與附件。
8. 設定角色與 RBAC 權限。
9. 管理總務 / 工務 / 主管 / 門市角色權限。
10. 管理使用者可見門市、部門、單位範圍。
11. 管理總務基礎設定，例如需求類型、設備 / 設施分類、料件分類、狀態設定、駁回原因與補資料類型。
12. 管理系統參數。
13. 查看稽核紀錄。
14. 處理資料異常修正。

系統管理員是總務服務中心的最高權限角色。
