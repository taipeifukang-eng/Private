## 產品承諾

讓門市用白話提出、追蹤並確認總務需求；讓總務從同一條可追溯流程完成受理、分流、執行、成本與資產紀錄，不再靠人腦、群組訊息或重複單據拼湊處理進度。

## 產品定位

總務服務中心不是單純報修系統，而是公司總務工作的紀錄與協作中心，範圍包含：

1. 門市維修、店內設施與現場狀況需求。
2. 庶務、設備、設施、料件與耗材添購。
3. 庫存出庫、門市調撥、收貨與異常處理。
4. 設備、設施、料件、架型與相容性主檔。
5. 廠商、服務區域、合作、採購、詢比議價與請款記錄。
6. 各地點水費、電費、電話費與網路費記錄。

## 使用者與情境

| 使用者 | 主要情境 | 核心需求 | 介面原則 |
|---|---|---|---|
| 門市店長 / 被指派人員 | 營業中遇到故障、缺料、添購或總務要求配合 | 快速送出、知道總務處理到哪、立即看到自己要做什麼 | 白話、少欄位、優先待我處理，不暴露內部術語 |
| 總務 | 每日受理、判斷、分流、採購、調撥與紀錄 | 先看要處理的案件，再看當前下一步與關聯單據 | 工作台導向、狀態真實、主動作單一明確、次要資料漸進展開 |
| 工務 | 處理已受理的維修派工 | 看現場、設備、照片、保固與處理進度 | 不承擔新需求受理、採購或庫存管理 |
| 主管 / 管理者 | 追蹤工作量、成本、逾期、廠商與異常 | 查看與比較，不直接改業務資料 | 報表和管理視角與執行工作台分離 |
| 系統管理員 | 權限、異常修正與系統維運 | 可管理全模組但仍需留存蹤跡 | 高風險動作需確認、防誤觸與可稽核 |

## 核心任務

### 1. 門市新增需求

- 先選「維修 / 現場狀況回報」或「庶務 / 料件添購補充」。
- 維修需求可選既有設備，但找不到主檔不得阻擋回報。
- 添購優先搜尋公司既有品項，仍保留建議採購新品與照片。
- 送出成功後必須離開可繼續編輯的表單狀態，清除或標記本機草稿已送出。

### 2. 門市「我的追蹤」

- 統一追蹤維修、添購、料件與總務發起的門市待辦。
- 預設優先顯示待門市回覆、補資料或確認的事項。
- 列表第一眼要看到門市、項目 / 現場描述、狀態與是否需要自己操作。
- 門市看到白話進度，不需理解工單中心、分流、內部階段等術語。
- 門市公開留言要有已讀狀態，並可看到由哪位總務讀取。

### 3. 總務需求工作台

- 統一承接待受理、待補資料、待複核、處理中、待門市確認與已完成需求。
- 開案後第一個問題是「這張單你要怎麼處理？」。
- 受理時必須選擇維修派工、採購評估、庫存出庫、調撥或資產異動等方向。
- 已分流到專責模組後，工作台只顯示處理節點、關聯單號與前往詳情，不在兩處編輯同一流程。
- 關聯工單、出庫、調撥、採購單號可點擊，用右側詳情查看。

### 4. 工單中心

- 只處理已受理且分流為維修派工的案件。
- 左側用於快速判斷門市、問題、現場描述、照片與下一步；右側優先顯示「目前要做什麼」。
- 處理紀錄與送門市確認是不同的明確動作。
- 已送門市確認後，不再把一般處理表單當成主要下一步。
- 工單與原需求的公開進度、留言、照片和門市確認必須同步。

### 5. 專責執行模組

- 料件處理中心承接出庫、調撥、採購與關聯單據，取代獨立「料件申請審核」。
- 調撥與收貨必須處理少收、未收、破損、收錯與取消。
- 採購成本、門市、廠商與請款分析放在採購 / 廠商報表，不塞進每日工作台。
- 設備 / 設施先有公司主檔或共用架型，再記錄各地點實際持有；不重複建立相同本質主檔。
- 料件狀態需分得出使用中、未使用 / 閒置、可調撥與異常。
- 設備、設施或共用架型與適配料件的相容性只建立一次，地點實體自動引用。

### 6. 帳單管理

- 紀錄水費、電費、電話費與網路費，可依地點、期間、帳號 / 路號 / 設備識別。
- 電費可登錄用電度數。
- 同一門市可有多條網路或多台設備需繳費。
- 每次登錄都可於新增當下上傳掃描檔或拍照。

## 資訊與系統狀態

介面必須完整處理：

- 載入中：不應因預設月份或大量資料阻擋使用者先選條件。
- 無資料：明確分辨「尚未查詢」、「查無結果」與「沒有權限」。
- 局部失敗：附件、留言或關聯單據失敗不應讓整頁失去其他已載入資訊。
- 權限拒絕：告知缺少的能力，不顯示虛假空資料。
- 重複送出：需有流水號、幂等或已送出草稿識別，不可生成重複單。
- 並行編輯：權限與高風險資料不可靜默覆蓋他人的新變更。
- 附件：多張照片要看得出數量並可檢視，但不重複顯示相同內容。

## 權限原則

1. `general_affairs.service_center.access` 只代表可進入，不等於可查看或管理所有總務資料。
2. 門市店長只能建立、查看、留言與確認自己被指派門市的需求。
3. 總部總務可執行總務業務模組，但不因此自動取得全系統 RBAC 管理權。
4. 督導與其他角色不預設取得總務權限；若未來需要區域查看，必須另定資料範圍與權限碼。
5. 系統管理員是總務服務中心最高權限角色，高風險動作仍需防呆與稽核。
6. UI、API、RLS 與資料範圍判斷必須一致。

## 非功能需求

- 主要桌機工作台需支援 1366px 以上長時間作業；門市回報與追蹤需支援手機。
- 不可依賴顏色單獨表達狀態；必須有文字或圖示輔助。
- 重要動作支援鍵盤焦點、足夠點擊範圍與明確禁用狀態。
- 查詢頁不應在進入時自動載入明顯廣範且耗時的資料。
- 列表、圖片、動態文字與長單號不得造成版面位移、重疊或溢出。
- 新版總務需求與舊跨部門總務單保持來源隔離，不自動搬移舊單。

## 介面概念決策

採用「調度桌 + 案件夾 + 執行單據」的工作隱喻：

- 調度桌：總務需求工作台，用於選案、判斷與分流。
- 案件夾：需求詳情與時間軸，保留原始描述、照片、留言與判斷蹤跡。
- 執行單據：工單、採購、出庫、調撥、資產異動與帳單，由各專責模組維護細節。

這是互動模型，不是裝飾主題。介面不應刻意繪製紙張、木桌、金屬面板或擬真物件。

## 絕不能發生

1. 門市送出成功後仍留在像是可重複送出的新增表單。
2. 同一草稿或同一次操作產生多張重複需求或工單。
3. 門市看到內部備註、成本、權限外資料或總務內部流程術語。
4. 已連結專責單據的案件可在兩個模組同時修改同一流程狀態。
5. 處理進度只儲存文字，但沒有實際推進系統狀態或門市可執行的下一步。
6. 總務需求、工單、門市追蹤與關聯單據對同一件事顯示互相衝突的狀態。
7. 「查看」權限無意間擴張成查看全部門市，或「管理」擴張成可刪除 / 強制結案。
8. 只因為無資料、權限錯誤或 API 逾時就顯示全部為 0。
9. 工作台充斥重複統計卡、說明卡、嵌套卡片或無法行動的提醒。
10. 為了視覺效果產生假狀態、假數據、無意義動畫或與業務無關的裝飾。

## 決策與已知邊界

- 已決定：門市只有「新增需求」與「我的追蹤」主入口，不再獨立顯示料件申請。
- 已決定：工作台完成受理與分流，專責模組完成實際執行細節。
- 已決定：總務工作台不顯示本月採購成本；成本分析放在採購 / 廠商報表。
- 已決定：公司與門市在資產持有上都視為地點；公司設備主檔不直接等於某地點已持有設備。
- 已決定：相容性先綁公司設備型號 / 設施架型，不針對每一座實體重複建立。
- 待驗證：工務正式角色、指派範圍與專屬權限碼尚需完整落地。
- 未來保留：主管高金額核准、預算控制、合約到期提醒與完整資產盤點。

## 驗收準則

- [ ] 門市可在不理解總務內部流程的情況下送出並追蹤需求。
- [ ] 門市進入「我的追蹤」後，3 秒內能分辨自己現在需要處理的事項。
- [ ] 總務打開案件後，3 秒內能判斷現場問題與目前下一步。
- [ ] 受理、補資料、駁回、分流、送門市確認與門市回報問題都有真實狀態與可恢復流程。
- [ ] 專責單據可從工作台點擊查看，且沒有兩處同時編輯同一流程。
- [ ] 門市、總務、工務與管理者只看到角色所需的資訊與動作。
- [ ] 桌機與手機無重疊、裁切、水平溢出或狀態變化造成的大幅位移。
- [ ] 介面不使用無功能的裝飾、假數據、重複摘要或嵌套卡片。
- [ ] 重要流程可透過單號、時間軸、已讀與操作者紀錄追溯。
