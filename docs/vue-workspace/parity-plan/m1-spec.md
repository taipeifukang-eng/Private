# M1 月結與獎金：最終規格

使用者於 2026-11-02 透過 M1 規格問卷確認。M1 所有開發、審查、測試子代理都必須遵守，與 `decisions.md`（D01–D18）衝突時以本文件為準。

原則：**預設照舊版行為**。下表是使用者拍板、與舊版不同或舊版未定義的地方。凡是「與舊版不同」的行為，都要在 `tests/parity/allowlist.json` 新增一筆 `approvedBy: null` 的條目（附 `match`），由主迴圈送給使用者核可。

## 決策

## 使用者補充（施作與後續規劃都要記住）

- **W01b-q2**：使用者希望新人升階最終由「人員異動紀錄」控制；這個提醒是早期沒有異動功能時的補救，現在的目的只是提醒店長確認每位新人的升階狀態。所以提醒不能阻擋儲存，也不要在此直接改職位。
- **W01b-q3**：影響獎金的關鍵是職位認定。不滿整月的專員以上，可能是調店、留職停薪、復職、離職等原因，不能猜成新進。
- **W04-q1**：之後要規劃版更內容的更新方式，並用一般使用者看得懂的寫法。列入 M9 前的待辦（不在 M1 範圍）。

## 驗收要求（每個工作項）

1. 四層測試（單元、冒煙、整合、e2e，desktop-1440 與 mobile-390）加 parity 全綠，才可 commit（D11）。
2. 金額相關：獎金計算用表格驅動單元測試同時呼叫舊版與新版，誤差 0 元；匯出 Excel 用 openpyxl 逐工作表、逐欄、逐格比對舊版輸出（同角色、同月份、同門市）。
3. 測試資料：DEV、VW/ZT 測試門市、保留月份 2099（月結）與 2038 年（績效），單次 fixture 測後由 sweeper 清除，孤兒 0（D15）。
4. 每個與舊版不同的行為都要有 allowlist 條目（`approvedBy: null` 且有 `match`），並在 parity 測試中被正確分類。
